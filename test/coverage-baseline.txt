# Go statement-coverage ratchet (issue #19).
#
# Format (one rule per line):
#   module <floor>            module-wide statement coverage
#   package <dir> <floor>     per-package statement coverage
#
# These floors are a ratchet. Raising a number as tests land is expected;
# lowering one, adding an exclusion, or removing a rule is a policy change
# that requires an explanation in the PR (see docs/testing.md). A missing
# coverage.out artifact fails the check outright.
#
# Rollout stages (documented so a silent drift is visible in review):
#   Stage 1 (2026-11): measured baseline with the handwritten entry point
#     and download-action paths covered; cmd/opentambo was 0% before.
#     Its main() stays unit-uncovered by design — it is exercised as an
#     instrumented subprocess by the integration suite (go build -cover +
#     GOCOVERDIR), which merges into coverage.integration.out and raises
#     this floor in Stage 2.
#   Stage 2: module floor 80%, cmd/opentambo floor including main().
#
# Calibration note (issue #15): the gate originally summed the raw profile
# directly. With -coverpkg=./... every test binary records every block, so
# that sum counted each statement once per test binary and reported diluted
# percentages (cmd/opentambo read 25.4% where the true figure was 76.2%).
# scripts/go-coverage.sh now canonicalizes the profile first (one record per
# block, covered when any test binary executed it). The floors below are
# the honest measurements with headroom; every number here is at or above
# the corresponding diluted-era floor, so the ratchet was never lowered.
#
# Calibration note (issue #16): the lifecycle package and its failure-
# injection suites raised the module measurement to 84.5% (cmd/opentambo
# 83.3%). Floors raised accordingly; headroom kept for CI scheduling.

package cmd/opentambo 80.0
